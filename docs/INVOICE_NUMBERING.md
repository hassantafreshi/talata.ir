# شماره‌گذاری قابل تنظیم فاکتور

> وضعیت: **پیاده‌سازی و آزموده**. کد: `app/Domain/Invoices/Numbering.php`، `SettingsController::numbering/saveNumbering`، `resources/views/app/numbering.blade.php`، `resources/js/pages/numbering.js`، `Digits::invoiceNumber()` / `invno()`. آزمون: `tests/Feature/InvoiceNumberingTest.php`. مسیر: «تنظیمات» ← «شماره‌گذاری فاکتور» (`/settings/numbering`، مجوز `settings.manage`، همه پلن‌ها).

## ۱. نیاز کاربر ایرانی (فرض‌های مستندشده، قابل تنظیم)

جستجوی وب منبع رسمی و واحدی برای شیوه شماره‌گذاری نرم‌افزارهای طلافروشی پیدا نکرد. بنابراین روش‌های زیر **فرض‌های رایج بازار**اند (کشف‌شده نیستند) و همه قابل تنظیم‌اند:

| نیاز | روش در زرلیو/طلاتا |
|---|---|
| هر سال از نوروز از ۱، با سال در شماره (رایج‌ترین) | پیش‌فرض: `1405-0001` |
| ادامه دفترچه فاکتور کاغذی (شماره پیوسته، بدون سال) | «فقط شماره پیوسته» + «شروع از شماره» (مثلاً ۲۵۰۱) |
| فروشگاه پرکار که شماره ماهانه می‌خواهد | «سال / ماه / شماره»: `1405/07/001` |
| چند شعبه یا چند دفتر، یا نوع کسب‌وکار در نسخه ۲ (طلا، نقره، سکه، آب‌شده) | پیشوند تا ۶ حرف/عدد: «حرف + سال - شماره» `ط-05-0001` |
| سامانه مؤدیان (بیرون از فاز ۱) | شماره داخلی هر فروشگاه یکتا و حداکثر ۳۲ نویسه است. قالب سریال مؤدیان باید هنگام اتصال بررسی شود |

## ۲. قواعد

- قالب: `[پیشوند][جداکننده][سال ۴ یا ۲ رقمی][جداکننده][ماه][جداکننده]شماره` (هر بخش خاموش حذف می‌شود). جداکننده `-`، `/` یا بدون. حداقل رقم شماره ۱ تا ۸ (با صفر پر می‌شود).
- شروع دوباره: هر سال (نوروز، تقویم شمسی و منطقه زمانی فروشگاه)، هر ماه، یا هیچ‌وقت.
- برای جلوگیری از شماره تکراری:
  - شروع سالانه سال را لازم دارد و شروع ماهانه سال و ماه را. ماه بدون سال هم مجاز نیست. سرور این‌ها را اعتبارسنجی می‌کند و صفحه همان لحظه هشدار می‌دهد.
  - ستون `invoices.number` برای هر فروشگاه یکتاست (قید پایگاه داده).
  - اگر بعد از تغییر قالب، شماره تازه با شماره‌ای که قبلاً صادر شده یکی شود، آن شماره **رد می‌شود و شماره بعدی** داده می‌شود؛ شماره‌ها هرگز دوباره استفاده نمی‌شوند.
- «شروع از شماره» فقط بزرگ‌تر از آخرین شماره صادرشده همان دوره پذیرفته می‌شود.
- شمارنده‌ها با کلید `(series='SALE', period_key)` نگهداری می‌شوند (`1405`، `1405-07` یا `ALL`). تخصیص شماره داخل تراکنش صدور و بعد از قفل ردیف فروشگاه انجام می‌شود. ذخیره تنظیمات هم همان قفل را می‌گیرد، پس در میانه صدور قالب عوض نمی‌شود.
- تنظیمات در `tenant_settings` (`key = invoice_numbering`) نسخه‌دار ذخیره می‌شوند (ذخیره هم‌زمان: `409 SETTINGS_CONFLICT`). هر تغییر با رویداد `settings.numbering_changed` (قبل/بعد) در لاگ فعالیت ثبت می‌شود.
- شماره صادرشده جزو snapshot است و با تغییر تنظیمات **هرگز عوض نمی‌شود**.
- **نمایش:** پیشوند حرفی ممکن است ترتیب نمایش را برعکس کند («۲۵۰۱-۰۵-ط»). `Digits::invoiceNumber()` (در Blade `invno()`) بعد از حروف یک علامت LRM می‌گذارد. همین قاعده در پیش‌نمایش JS، چاپ، صفحه عمومی و متن پیامک هم اعمال شده است.
- `series` برای «فاکتور خرید» نسخه ۲ (`PURCHASE`) آماده است.

## ۳. UI و UX (موبایل‌اول)

- کادر بزرگ بالای صفحه «شماره فاکتور بعدی» را با دو شماره بعدی نشان می‌دهد و با هر تغییر بلافاصله به‌روز می‌شود.
- «یک روش را انتخاب کنید»: چهار کارت بزرگ (نام، نمونه واقعی با تاریخ امروز و یک خط توضیح ساده).
- «تنظیم دقیق» (باز شونده): پیشوند، سال (۱۴۰۵ / ۰۵ / بدون سال)، «ماه هم بیاید»، «از کِی دوباره از ۱ شروع شود؟» (هر سال / هر ماه / هیچ‌وقت)، جداکننده و حداقل رقم. اگر انتخاب‌ها با هیچ روش آماده‌ای جور نباشد، این بخش خودکار باز می‌شود.
- «شروع از شماره (اختیاری)» با توضیح دفترچه کاغذی. یادداشت «تغییر از فاکتور بعدی اعمال می‌شود؛ شماره N فاکتور قبلی عوض نمی‌شود».
